# 레슨 음성 녹음 시스템 v2 — 기획서

> 상태: **초안 (결정 대기)** · 대상: 코치 앱 "레슨 동반" 녹음·받아쓰기·요약
> 대체 대상: `services/lessonAudioPipeline.ts`, `hooks/useLiveTranscription.ts`,
> `components/LiveLessonCompanion.tsx`의 녹음/전사 부분

---

## 1. 왜 새로 만드나 — 현 구조 진단

최근 PR(#469 ~ #478) 10건 가까이가 전부 같은 기능의 땜질이었다.
"받아쓰기가 조용히 멈춘다", "하지 않은 말이 적힌다", "필기가 빠진다",
"용어가 틀린다". 개별 버그가 아니라 **구조가 만드는 버그**다.

| 규모 | |
|---|---|
| `lessonAudioPipeline.ts` | 3,749줄 |
| `useLiveTranscription.ts` | 446줄 |
| `LiveLessonCompanion.tsx` | 1,281줄 |
| 녹음·전사 관련 테스트 | 20개 이상 (대부분 회귀 방지용) |

### 근본 원인 5가지

1. **받아쓰기 엔진이 둘이다.** 기기 인식기(네이티브/Web Speech)를 쓰다가
   죽으면 Gemini 청크 전사로 넘어간다. 감시견(watchdog), 연속 실패 카운트,
   재시작 백오프, degraded 전환… 상태 조합이 폭발하고, 그 틈에서
   "아무도 받아 적지 않는 상태"가 생긴다.
2. **마이크를 두 주체가 나눠 잡는다.** 기기 인식기와 MediaRecorder가 같은
   마이크를 동시에 잡으면 인식기가 **오류 없이 조용히 죽는** 기기가 있다.
   정책이 "인식 중엔 녹음 안 함" → "둘 다 켬 + 감시견"으로 바뀌었고,
   코드 주석끼리도 서로 모순된다(`useLiveTranscription.ts` 머리말 vs
   `LiveLessonCompanion.tsx` 시작 핸들러). 경합 자체를 없애지 않는 한
   계속 증상만 막게 된다.
3. **범용 LLM을 STT로 쓴다.** 8초 조각을 Gemini에 보내면, 무음·타구음
   구간에서 그럴듯한 대화를 지어낸다. 이를 막으려고 VAD 게이트, 오버랩
   트림, 재전달 중복 제거, 헤더 바이트 스캔 같은 방어 코드가 계속 붙었다.
4. **오디오가 기기에만 있다.** IndexedDB에 쌓아 두었다가 종료 시 한 번에
   업로드한다. 50분 레슨의 업로드 실패·앱 종료는 곧 기록 유실이다.
5. **후처리가 다단계 AI 호출이다.** 라이브 교정 → 정밀 전사(5분 슬라이스)
   → 오디오 대조 → 최종 교정 → 화자 분류 → 이중 요약. 단계마다 비용·지연·
   실패 지점이 하나씩 늘었다.

## 2. 목표와 비목표

### 목표 (성공 지표)

| 지표 | 목표 |
|---|---|
| 원본 오디오 유실 | **0건** — 녹음 시작~종료 구간이 100% 서버에 도달 |
| 무음 구간 창작 | **0건** — 말하지 않은 문장이 기록에 남지 않음 |
| 골프 용어 정확도 | 골든셋 기준 용어 정확도 ≥ 95% (PoC에서 기준선 측정) |
| 종료 → 검토 화면 | 50분 레슨 기준 ≤ 90초 |
| 라이브 미리보기 지연 | ≤ 2초 (라이브를 유지하는 경우) |
| 코드 규모 | 녹음·전사 클라이언트 코드 현재의 1/3 이하 |

### 비목표

- 학생 앱 녹음 (이번 범위는 코치 앱)
- 영상 녹화와의 통합 (기존 클립 촬영은 그대로 둔다)
- 다국어 (한국어 우선)

## 3. 설계 원칙

1. **녹음과 받아쓰기를 분리한다.** 녹음은 무슨 일이 있어도 멈추지 않는
   단일 경로다. 받아쓰기가 실패해도 녹음은 계속되고, 나중에 원본으로
   다시 받아 적을 수 있다.
2. **마이크는 한 번만 연다.** 하나의 오디오 스트림을 녹음기와 라이브
   전송에 나눠 준다(fan-out). 경합 자체가 생기지 않는다.
3. **받아쓰기는 전용 STT 하나.** LLM은 오디오를 듣지 않는다. LLM은
   STT가 만든 **텍스트만** 다룬다(용어 교정, 요약).
4. **진실의 원천은 서버의 원본 오디오.** 라이브 텍스트는 "미리보기"일
   뿐이고, 최종 기록은 원본 전체를 한 번에 배치 전사한 결과다.
5. **오디오는 레슨 중 계속 서버로 올라간다.** 기기 저장소는 업로드 대기
   버퍼일 뿐이다.
6. **상태는 명시적 상태 머신 하나로 관리한다.** 플래그 조합 금지.

│       │                                               │  │

│                                                       │  │  │
│  RecordingSession (상태 머신)                          │  │  │
└───────────────────────────────────────────────────────┘  │  │
                                                           ▼  ▼
┌─────────────────────── 서버 ──────────────────────────────────┐
│  R2: recordings/{id}/chunk-0001.webm …                         │
│                                                               │
│  /api/recordings/:id/live (WS) ──▶ 스트리밍 STT ──▶ 잠정 텍스트 │
│                                                               │
│  POST /complete ──▶ 처리 잡                                    │
│     1. 청크 결합 → 원본 파일                                    │

│     3. LLM 텍스트 교정 1회 (용어 사전 기반, 수정 범위 제한)        │
│     4. LLM 요약 1회 (코치 요약 · 학생 요약)                       │
│     5. 완료 → 푸시 알림                                         │

### 4.1 클라이언트 모듈 (새로 작성)

| 모듈 | 책임 | 예상 규모 |
|---|---|---|
| `recording/RecordingSession.ts` | 상태 머신, 시작/일시정지/재개/종료 | ~300줄 |
| `recording/ChunkUploader.ts` | IndexedDB 큐, presigned 업로드, 재시도, 오프라인 버퍼 | ~200줄 |
| `recording/LivePreviewStream.ts` | AudioWorklet → PCM → WebSocket, 잠정 텍스트 수신 | ~200줄 |
| `recording/micStream.ts` | 마이크 획득·끊김 감지·재획득 | ~100줄 |
| `components/RecordingPanel.tsx` | 녹음 UI (타이머, 레벨 미터, 업로드 상태, 미리보기) | ~300줄 |

**사라지는 것:** 기기 인식기 엔진 2종, watchdog, VAD 게이트, 헤더 바이트
스캔(`findInitSegmentEnd`), 재전달 중복 제거, 오버랩 트림, 라이브 교정,
`@capacitor-community/speech-recognition` 의존성.

> 청크는 독립 재생 가능할 필요가 없다. 라이브 텍스트는 별도 PCM 스트림이
> 맡고, 청크는 서버에서 순서대로 이어 붙여 한 파일로만 쓰기 때문이다.

### 4.2 서버 (새로 작성)

| 엔드포인트 | 설명 |
|---|---|
| `POST /api/recordings` | 세션 생성 (레슨·학생·코치 연결), id 발급 |
| `POST /api/recordings/:id/chunks/:seq/url` | 청크 presigned PUT URL |
| `POST /api/recordings/:id/chunks/:seq/ack` | 업로드 확인 (크기·해시) |
| `WS /api/recordings/:id/live` | 스트리밍 STT 프록시 (API 키는 서버에만) |
| `POST /api/recordings/:id/complete` | 녹음 종료 → 처리 잡 시작 |
| `GET /api/recordings/:id` | 상태·진행률·결과 조회 |

서버는 현재 Express + pg + R2 구성이고 WebSocket이 없다.
라이브 미리보기를 유지하면 `ws` 패키지 추가가 필요하다.
처리 잡은 우선 프로세스 내 큐(DB 상태 기반, 재시작 시 재개)로 시작하고,
부하가 생기면 Render 백그라운드 워커로 분리한다.

### 4.3 데이터 모델

```sql
lesson_recordings (
  id, coach_id, client_id, lesson_id NULL,
  status,              -- recording | uploading | processing | ready | failed
  mime_type, duration_ms, started_at, ended_at,
  stt_provider, error, created_at, updated_at
)

recording_chunks (
  recording_id, seq, r2_key, bytes, sha256, duration_ms, uploaded_at,
  PRIMARY KEY (recording_id, seq)
)

transcript_segments (
  recording_id, idx, start_ms, end_ms,
  speaker,             -- coach | student | unknown
  raw_text,            -- STT 원문 (보존)
  text,                -- 교정 후 (코치 수정 포함)
  confidence, edited_by_coach bool
)
```

`raw_text`를 항상 보존해 교정이 원문을 망쳤는지 추적한다.
기존 `LiveLessonDetail.transcript`는 출력 포맷으로 유지하고,
`recordingId` 필드만 추가해 기존 화면(검토·스토리)과 호환한다.

## 5. 녹음 상태 머신

```
 idle ─▶ acquiring_mic ─▶ recording ⇄ paused
                             │  ▲
               mic_lost ─────┘  └── reacquired
                             │
                             ▼
                        finalizing   (마지막 청크 flush, 업로드 대기)
                             │
                             ▼
                        processing   (서버 — 앱 닫아도 됨)
                             │
                     ┌───────┴───────┐
                     ▼               ▼
                   ready           failed (재시도 가능, 원본은 보존)
```

- **오프라인:** 상태는 `recording` 그대로, 청크는 IndexedDB에 쌓이고
  UI에 "업로드 대기 N개"만 표시. 연결되면 자동 재개.
- **앱 강제 종료:** 다음 실행 시 업로드 안 된 청크가 있으면 업로드 재개
  → 서버에 이미 올라간 청크와 합쳐 복구. (현 구조와 달리 "기기에서
  전체를 다시 조립"할 필요가 없다.)
- **마이크 끊김(전화 수신 등):** `mic_lost`에서 재획득 시도, 녹음 공백은
  타임라인에 표시.

## 6. 받아쓰기 엔진 선정 (PoC로 결정)

LLM이 아닌 **전용 STT** 중에서, 아래 조건을 우리 레슨 녹음으로 직접 비교해
고른다. 스펙은 업체 문서 기준이므로 PoC에서 반드시 실측한다.

| 필수 조건 | 이유 |
|---|---|
| 한국어 품질 | 기본 |
| 키워드 부스팅 / 사용자 사전 | 골프 용어 (페이스, 다운스윙, 릴리스…) |
| 화자 분리 | 코치 / 학생 구분 (현재 LLM 추측으로 함) |
| 단어·구간 타임스탬프 | 텍스트 탭 → 원본 재생 |
| 스트리밍 API | 라이브 미리보기 (유지 시) |
| 50분 장문 배치 | 최종 전사 |

**후보:**

- **리턴제로(RTZR) STT** — 한국어 특화, 스트리밍·화자분리·키워드 부스팅
- **네이버 CLOVA Speech** — 한국어 특화, 장문·화자분리·키워드 부스팅
- **Google Cloud Speech-to-Text v2 (Chirp)** — 기존 Google 인증 재사용 가능, 구문 적응(phrase set)

평가 항목: 문자 오류율(CER), 골프 용어 정확도, 화자 분리 정확도,
무음 구간 창작 여부, 분당 단가, 지연 시간.

## 7. 코치 사용 흐름 (UX)

1. **시작** — 학생 선택 → "녹음 시작". 마이크 권한은 이 시점에 한 번.
2. **녹음 중** — 큰 타이머, 실시간 레벨 미터(마이크가 살아 있다는 증거),
   업로드 상태 점(초록: 동기화됨 / 노랑: 대기 N개).
   라이브 미리보기는 회색 잠정 텍스트로 흐른다 — "기록"이 아니라
   "듣고 있다"는 신호.
3. **종료** — "정리 중이에요. 앱을 닫아도 됩니다." 완료 시 푸시 알림.
4. **검토** — 화자별로 나뉜 필기 + 코치 요약 / 학생 요약.
   각 줄을 탭하면 **그 구간 원본이 재생**된다 → 코치가 직접 듣고 고친다.
   AI가 교정한 단어는 밑줄로 표시하고, 원문과 비교할 수 있다.
5. **저장** — 기존 레슨 기록 / 레슨 스토리로 연결.

라인-오디오 연결(4번)이 신뢰의 핵심이다. 지금은 "AI가 맞게 적었는지"
코치가 확인할 방법이 없다.

## 8. 단계별 계획

| 단계 | 내용 | 완료 기준 | 기간(추정) |
|---|---|---|---|
| **0. PoC** | 실제 레슨 녹음 5건 확보 → 정답 전사 작성 → STT 후보 3종 비교 | 엔진 결정, 골든셋을 `evals/`에 등록 | 3–5일 |
| **1. 녹음 코어** | RecordingSession + ChunkUploader + 서버 청크 API + DB | 50분 녹음·오프라인·강제 종료 시나리오에서 유실 0 | 1주 |
| **2. 배치 처리** | 결합 → 배치 STT → 교정 1회 → 요약 1회 → 검토 화면 연결 | 종료→검토 ≤ 90초, 골든셋 지표 달성 | 1주 |
| **3. 라이브 미리보기** | AudioWorklet + WS + 스트리밍 STT | 지연 ≤ 2초, 실패해도 녹음 무영향 | 3–5일 |
| **4. 네이티브 백그라운드** | 화면 꺼짐·앱 전환 중 녹음 유지 (네이티브 녹음 플러그인) | iOS/Android 화면 꺼진 채 50분 녹음 | 1주 |
| **5. 전환·정리** | 기능 플래그로 코치 3명 dogfood → 전체 전환 → 구 코드 삭제 | 구 파이프라인 제거 | 1주 |

1단계만으로도 "녹음이 안 남는다"는 가장 큰 문제가 해결된다.
라이브 미리보기(3단계)는 녹음·최종 기록과 독립적이라 나중에 붙여도 된다.

## 9. 리스크

| 리스크 | 대응 |
|---|---|
| WebView는 화면이 꺼지면 녹음이 멈춤 (특히 iOS) | 4단계 네이티브 녹음. 그 전까지는 화면 켜짐 유지(keep-awake) + 안내 |
| STT 업체 의존 | `SttProvider` 인터페이스로 추상화, 배치/스트리밍 교체 가능하게 |

| 진행 중 레슨의 구 IndexedDB 세션 | 전환 시 구 세션 복구 경로는 한 릴리스 동안 유지 후 제거 |
| 개인정보 (학생 음성 서버 보관) | 기존 동의(consents) 흐름에 녹음 보관 항목 추가, 보관 기간 정책 |
