# 레슨 음성 녹음 시스템 v2 — 기획서

> 상태: **확정 (v1.2) · 1단계 구현 중** — 진행 현황은 맨 아래 12장 · 대상: 코치 앱 "레슨 동반" 녹음 → 받아쓰기 → 요약
> 대체 대상: `services/lessonAudioPipeline.ts`, `hooks/useLiveTranscription.ts`,
> `components/LiveLessonCompanion.tsx`의 녹음/전사 부분

## 0. 확정된 결정

| # | 결정 | 설계에 미치는 영향 |
|---|---|---|
| 1 | **실시간 받아쓰기 없음** | 레슨 중에는 녹음만 한다. 받아쓰기는 레슨이 끝난 뒤 원본 전체로 한 번. 기기 인식기·스트리밍·WebSocket이 전부 빠진다 |
| 2 | **받아쓰기 엔진은 비교해서 가장 뛰어난 것** | PoC에서 후보 엔진을 실제 레슨 녹음으로 채점해 1위를 쓴다 (6장) |

| 4 | **화면이 꺼진 상태에서 녹음돼야 함 (레슨 중 화면은 꺼둔다)** | 웹뷰 녹음으로는 불가 → **네이티브 녹음이 1단계 필수** (4장) |

## 1. 왜 새로 만드나 — 현 구조 진단

최근 PR(#469 ~ #478) 10건 가까이가 전부 같은 기능의 땜질이었다.
"받아쓰기가 조용히 멈춘다", "하지 않은 말이 적힌다", "필기가 빠진다",
"용어가 틀린다". 개별 버그가 아니라 **구조가 만드는 버그**다.

| 규모 | |
|---|---|
| `lessonAudioPipeline.ts` | 3,749줄 |
| `useLiveTranscription.ts` | 446줄 |
| `LiveLessonCompanion.tsx` | 1,281줄 |
| 녹음·전사 관련 테스트 | 20개 이상 (대부분 회귀 방지용) |

### 근본 원인

1. **받아쓰기 엔진이 둘이다.** 기기 인식기를 쓰다가 죽으면 Gemini 조각
   전사로 넘어간다. 감시견·실패 카운트·재시작 백오프… 상태 조합이 폭발하고,
   그 틈에서 "아무도 받아 적지 않는 상태"가 생긴다.
2. **마이크를 두 주체가 나눠 잡는다.** 인식기와 녹음기가 같은 마이크를
   잡으면 인식기가 오류 없이 조용히 죽는 기기가 있다. 정책이 여러 번 바뀌어
   코드 주석끼리도 서로 모순된다.
3. **범용 LLM을 받아쓰기에 쓴다.** 8초 조각을 Gemini에 보내면 무음·타구음
   구간에서 그럴듯한 대화를 지어낸다. 방어 코드가 계속 붙었다.
4. **오디오가 기기에만 있다가 종료 시 한 번에 올라간다.** 업로드 실패·앱
   종료는 곧 기록 유실이다.
5. **웹뷰에서 녹음한다.** 화면이 꺼지거나 앱이 백그라운드로 가면 웹뷰의
   녹음·JS가 멈춘다(특히 iOS). 화면을 끄고 레슨하는 실제 사용 방식과 맞지 않는다.
6. **후처리가 다단계 AI 호출이다.** 라이브 교정 → 정밀 전사 → 오디오 대조 →
   최종 교정 → 화자 분류 → 이중 요약.

## 2. 목표

| 지표 | 목표 |
|---|---|
| 원본 오디오 유실 | **0건** — 화면 꺼진 채 50분 녹음해도 전 구간이 서버에 도달 |
| 무음 구간 창작 | **0건** |
| 골프 용어 정확도 | 골든셋 기준 ≥ 95% (PoC에서 기준선 측정) |
| 종료 → 결과 준비 | 50분 레슨 기준 ≤ 3분, 완료 시 푸시 알림 |
| 배터리 | 50분 녹음에 배터리 소모 ≤ 5% (화면 꺼짐 기준) |
| 코드 규모 | 녹음·전사 클라이언트 코드 현재의 1/4 이하 |

**비목표:** 레슨 중 실시간 받아쓰기, 학생 앱 녹음, 영상 녹화 통합, 다국어.

## 3. 설계 원칙

1. **레슨 중에는 녹음만 한다.** 받아쓰기·요약은 전부 레슨이 끝난 뒤 서버에서.
2. **녹음은 네이티브가 한다.** 웹뷰는 시작·종료 버튼과 결과 화면만 맡는다.
3. **오디오는 레슨 중 1분 단위로 서버에 올라간다.** 기기 저장소는 업로드
   대기 버퍼일 뿐이다. 업로드도 네이티브가 한다(화면 꺼짐 중에도).
4. **받아쓰기는 전용 엔진 하나.** LLM은 엔진이 만든 **텍스트만** 다룬다.
5. **진실의 원천은 서버의 원본 오디오.** 기록의 모든 줄은 원본의 시간
   구간과 연결된다.
6. **상태는 명시적 상태 머신 하나.**

### 4.1 네이티브 녹음 플러그인 `LessonRecorder` (새로 작성)

화면 꺼짐 녹음 + 백그라운드 업로드를 지원하는 기성 Capacitor 플러그인이
없어 직접 만든다. iOS(Swift)·Android(Kotlin) 각 400~600줄 예상.

**공통 사양**
- 포맷: AAC-LC, 모노, 16kHz, 32kbps (음성 받아쓰기에 충분, 50분 ≈ 12MB)
- 60초마다 세그먼트 파일을 닫고 다음 파일 시작. 세그먼트마다 단독 재생 가능
  (현 구조의 헤더 바이트 스캔 같은 꼼수 불필요). 세그먼트 사이 공백 없이 이어지게
  Android는 `setNextOutputFile`(API 26+), iOS는 녹음기 두 개 교대.
- 닫힌 세그먼트는 즉시 업로드 큐로. 업로드 성공 시 기기에서 삭제.
- 업로드 인증: 녹음 시작 시 서버가 발급하는 **녹음 전용 토큰**
  (해당 recording에만 쓰기 가능, 유효 12시간). 로그인 토큰이 레슨 중
  만료돼도 업로드가 끊기지 않는다.
- 이벤트(웹뷰로): `state`, `segmentUploaded`, `interrupted`, `level`(화면 켜졌을 때만).

**iOS**
- `Info.plist`에 `UIBackgroundModes: audio` 추가 → 화면 꺼짐·잠금 중 녹음 유지
- `AVAudioSession` 카테고리 `.record`, 인터럽션(전화 수신) 감지 →
  종료 후 자동 재개, 공백 구간을 메타데이터로 기록
- 업로드: 백그라운드 `URLSession` (앱이 정지돼도 OS가 이어서 업로드)
- 상태바 주황 점 = 녹음 중 (OS 기본 표시)

**Android**
- 포그라운드 서비스 `foregroundServiceType="microphone"` +
  `FOREGROUND_SERVICE_MICROPHONE` 권한 (Android 14+ 필수)
- 상시 알림 "레슨 녹음 중 · 00:32:10" + [종료] 버튼 → 화면을 켜지 않고도 종료 가능
- 업로드: WorkManager (네트워크 조건부, 재시도)
- 제조사 배터리 최적화(삼성 등)로 서비스가 죽는 경우 대비: 첫 사용 시
  배터리 최적화 예외 요청 안내

**웹(브라우저) 코치 앱:** 화면 꺼짐 녹음이 원리적으로 불가. 녹음 기능은
네이티브 앱 전용으로 하고, 웹에서는 "앱에서 녹음하세요" 안내만 한다.

### 4.2 서버 API

| 엔드포인트 | 설명 |
|---|---|
| `POST /api/recordings` | 세션 생성(코치·학생·레슨), 녹음 전용 토큰 발급 |
| `PUT /api/recordings/:id/segments/:seq` | 세그먼트 업로드 → R2 (멱등, 재전송 안전) |
| `POST /api/recordings/:id/complete` | 종료 선언(총 세그먼트 수 포함) → 누락 없으면 처리 잡 시작 |
| `GET /api/recordings/:id` | 상태·진행률·결과 |
| `POST /api/recordings/:id/keep` / `DELETE …/keep` | 원본 보관 / 보관 해제 |
| `GET /api/recordings/storage` | 내 보관 사용량 / 한도 |

- 처리 잡: DB 상태 기반 큐(서버 재시작 시 재개). 기존 `scheduledPushRunner`와
  같은 방식으로 시작하고, 부하가 생기면 Render 백그라운드 워커로 분리.
- 세그먼트 결합에 `ffmpeg-static` 추가.
- `complete`가 왔는데 일부 세그먼트가 아직 업로드 중이면 `uploading` 상태로
  대기하다 모두 도착하면 자동 진행 (코치는 기다릴 필요 없음).

### 4.3 데이터 모델

```sql
lesson_recordings (
  id, coach_id, client_id, lesson_id NULL,
  status,            -- recording | uploading | processing | ready | failed
  duration_ms, segment_count, bytes,
  started_at, ended_at,
  audio_expires_at,  -- 기본 ended_at + 3일, 보관 시 NULL
  kept_at NULL,      -- 코치가 보관을 누른 시각
  audio_deleted_at NULL,
  stt_engine, error, created_at, updated_at
)

recording_segments (
  recording_id, seq, r2_key, bytes, duration_ms, uploaded_at,
  PRIMARY KEY (recording_id, seq)
)

recording_gaps (     -- 전화 수신 등으로 녹음이 끊긴 구간
  recording_id, start_ms, end_ms, reason
)

transcript_segments (
  recording_id, idx, start_ms, end_ms,
  speaker,           -- coach | student | unknown
  raw_text,          -- 엔진 원문 (항상 보존)
  text,              -- 교정 후 (코치 수정 포함)
  confidence, edited_by_coach bool
)
```

받아쓰기·요약 텍스트는 **영구 보관**한다. 3일 후 지워지는 것은 원본 오디오뿐이다.
기존 `LiveLessonDetail.transcript`는 출력 포맷으로 유지하고 `recordingId`만
추가해 기존 검토·스토리 화면과 호환한다.

## 5. 녹음 상태 머신

```
 idle ─▶ starting ─▶ recording ─▶ interrupted ─▶ recording
                        │            (전화 등, 끝나면 자동 재개)
                        ▼
                    finishing   (마지막 세그먼트 닫기)
                        │
                        ▼
                    uploading   (남은 세그먼트 전송 — 앱 꺼도 OS가 계속)
                        │
                        ▼
                    queued      (세그먼트가 모두 도착 — 처리 대기)
                        │
                        ▼
                    processing  (서버)
                        │
                ┌───────┴───────┐
                ▼               ▼
              ready          failed  (원본은 남아 있어 재처리 가능)
```

- **오프라인 / 와이파이 불안정:** 녹음은 그대로, 세그먼트는 기기에 쌓였다가
  연결되면 자동 업로드.
- **앱 강제 종료 / 기기 재부팅:** 다음 실행 시 기기에 남은 세그먼트를 업로드하고
  "녹음이 중간에 끊겼어요. 여기까지 정리할까요?"를 묻는다.
- **저장 공간 부족:** 시작 전 여유 공간 확인(최소 200MB), 레슨 중 부족해지면
  알림으로 경고.

## 6. 받아쓰기 엔진 선정 PoC

### 방법
1. 실제 레슨 녹음 **5건** 확보 (조용한 실내 / 시끄러운 타석 / 코치 2명 이상 섞어서).
   새 녹음 형식(AAC 16kHz 32kbps)으로 녹음해 실제 조건과 같게.
2. 각 녹음의 **정답 받아쓰기** 작성 (화자 표시 포함) → `evals/`에 골든셋으로 등록.
   이후 엔진 교체·회귀 검사에도 계속 쓴다.
3. 후보 전부에 같은 파일 + 같은 골프 용어 사전을 넣고 자동 채점.

### 후보
실시간이 빠져 스트리밍 지원은 조건이 아니다. 배치 정확도로만 겨룬다.

- 리턴제로(RTZR) STT
- 네이버 CLOVA Speech
- Google Cloud Speech-to-Text v2 (Chirp)
- ElevenLabs Scribe
- OpenAI 받아쓰기 모델
- (기준선) 현재 방식 — Gemini

### 채점

| 항목 | 비중 | 비고 |
|---|---|---|
| **무음 구간 창작** | 통과/탈락 | 타구음·무음 구간에 문장이 생기면 탈락 |
| 골프 용어 정확도 | 35% | 용어 사전 단어 기준 |
| 문자 오류율(CER) | 25% | |
| 화자 분리 정확도 | 20% | 코치/학생 구분 |
| 분당 단가 | 10% | |
| 처리 시간 | 10% | 50분 파일 기준 |

1위 엔진을 채택하고, 엔진은 `SttEngine` 인터페이스 뒤에 두어 나중에 더 좋은
엔진이 나오면 골든셋으로 다시 채점해 교체한다.

## 7. 원본 보관 정책 · 플랜 연동

### 기본 규칙
- 모든 레슨 원본은 **종료 3일 후 자동 삭제**. 받아쓰기·요약은 영구 보관.
- 코치가 레슨 기록에서 **[원본 보관]**을 누르면 자동 삭제에서 제외.
- 삭제 하루 전 앱 내 표시: "내일 원본이 삭제돼요 · 보관하기".
- 원본이 있는 동안에는 받아쓰기 각 줄을 누르면 해당 구간이 재생된다.
  삭제된 뒤에는 텍스트만 남는다.

### 보관 용량 — 시간 단위로 표시
코치에게 MB/GB는 와닿지 않으므로 **"보관 시간"**으로 표시한다.
(32kbps 기준 1시간 ≈ 14MB, R2 저장 비용은 1시간당 월 0.3원 수준이라 원가 부담은 작다.
플랜 구분은 원가보다 가치 기준으로 정한다.)

| 플랜 | 보관 한도 (제안) | 대략 |
|---|---|---|
| FREE | 녹음 기능 없음 (현재와 같이 유료 기능) | — |
| PRO | **20시간** | 50분 레슨 약 24개 |
| PRO 플러스 (신설) | **100시간** | 약 120개 |
| PRO 맥스 (신설) | **500시간** | 약 600개 |

한도 확정(2026-11-16). 플러스·맥스 월 가격은 미정.

### 한도 초과 시
- 보관 한도를 넘는 [원본 보관]은 막고 "보관 공간이 가득 찼어요" + 상위 플랜 안내.
- **이미 보관한 원본은 절대 자동 삭제하지 않는다.** 코치가 직접 보관 해제하거나
  상위 플랜으로 올린다.
- 플랜을 내리거나 구독이 끝나 한도를 넘게 되면: 30일 유예 + 알림 3회
  (30일·7일·1일 전) 후 **오래된 보관분부터** 삭제. 받아쓰기·요약은 그대로.
- 설정 화면에 "보관 사용량 14.2 / 20시간" 막대 + 보관 목록(정리용).

> 참고: 현재 결제 화면에 PRO 가격이 29,000원 / 29,900원 두 가지로 섞여
> 표시된다(`components/SubscriptionModal.tsx`). 플랜 신설 시 함께 정리.

## 8. 코치 사용 흐름

1. **시작** — 학생 선택 → [녹음 시작]. 첫 사용 시에만 마이크·알림·
   (안드로이드) 배터리 최적화 예외 안내.
2. **녹음 중** — "녹음 중이에요. 화면을 꺼도 됩니다." 큰 타이머 하나.
   화면을 끄고 레슨한다. 안드로이드는 알림창에서, iOS는 앱을 열어 종료.
3. **종료** — [레슨 종료] → "정리하고 있어요. 앱을 닫아도 돼요."
4. **알림** — 약 3분 내 "OOO 회원 레슨 정리가 끝났어요" 푸시.
5. **검토** — 화자별 받아쓰기 + 코치 요약 / 학생 요약. 줄을 누르면 해당
   구간 원본 재생(3일간 또는 보관 시). AI가 고친 단어는 밑줄, 원문 비교 가능.
   하단에 "원본은 11월 19일에 삭제돼요 · [보관하기]".
6. **저장** — 기존 레슨 기록 / 레슨 스토리로 연결.

## 9. 단계별 계획

| 단계 | 내용 | 완료 기준 | 기간(추정) |
|---|---|---|---|
| **0. PoC** | 레슨 녹음 5건 + 정답 받아쓰기 → 엔진 6종 채점 | 엔진 결정, 골든셋 `evals/` 등록 | 1주 |
| **1. 네이티브 녹음** | `LessonRecorder` 플러그인(iOS·Android) + 세그먼트 업로드 API + DB | 실기기에서 화면 꺼짐 50분·전화 수신·와이파이 끊김·강제 종료 시나리오 전부 유실 0 | 2주 |
| **2. 서버 처리** | 결합 → 받아쓰기 → 교정 1회 → 요약 1회 → 푸시 → 검토 화면 | 종료→알림 ≤ 3분, 골든셋 지표 달성 | 1주 |
| **3. 보관 정책** | 3일 자동 삭제 잡, 보관하기, 용량 쿼터, 플랜 연동, 설정 화면 | 정책대로 삭제·차단·유예 동작 | 1주 |
| **4. 전환·정리** | 기능 플래그로 코치 3명 dogfood → 전체 전환 → 구 코드·`speech-recognition` 의존성 삭제 | 구 파이프라인 제거 | 1주 |

0단계와 1단계는 병행 가능하다(엔진과 녹음은 서로 독립).
1단계는 실기기 테스트가 필수라 iOS·Android 기기 각 1대 이상이 필요하다.

## 12. 진행 현황

### 1단계 — 완료(코드), 실기기 검증 대기

| 영역 | 파일 | 상태 |
|---|---|---|
| DB | `server/migrations/1755400000012_lesson-recordings.js` | 완료 |
| 정책(보관 3일·플랜 한도·업로드 토큰) | `server/src/services/recordingPolicy.ts` | 완료, 단위 테스트 16개 |
| API | `server/src/routes/recordings.ts` | 완료, 실제 Postgres로 23개 시나리오 검증 |
| 원본 정리 러너(매시간) | `server/src/services/recordingRetentionRunner.ts` | 완료 |
| 앱 JS 연결 | `services/recording/*` | 완료, 단위 테스트 5개 |
| Android 녹음기 | `plugins/lesson-recorder/android` | 작성 완료 — 빌드·실기기 검증 필요 |
| iOS 녹음기 | `plugins/lesson-recorder/ios` | 작성 완료 — Xcode 빌드·실기기 검증 필요 |

구현 메모
- 세그먼트 경계 무손실: Android는 AudioRecord(PCM)→MediaCodec(AAC)→MediaMuxer, iOS는
  AVAudioEngine→AVAudioConverter(16kHz)→AVAudioFile. 둘 다 입력은 끊지 않고 파일만 교체.
- 업로드: Android WorkManager, iOS 백그라운드 URLSession. 서버는 재전송을 멱등 처리.
- 녹음 서비스 선언(Android)과 백그라운드 오디오(iOS)는 **코치 앱에만** 넣었다.
  학생 앱에는 플러그인 코드만 들어가고 `isAvailable()`이 false.
- 앱이 강제 종료되면 쓰던 세그먼트 하나(최대 60초)는 복구 불가. 나머지는 다음 실행 때 이어서 올라간다.
- Android는 통화 중 OS가 마이크에 무음을 넣으므로 공백 기록이 없다. iOS는 인터럽션을 공백으로 기록.
